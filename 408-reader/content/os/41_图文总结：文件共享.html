在一个多用户的操作系统中，每个用户都会有自己的文件目录，比如在根目录下面有两个用户的目录，分别是laotang 的，还有一个是 xiaoming 的，在 laotang 目录下有多个文件，在 xiaoming 目录下也有多个不同文件
现在 xiaoming 对 laotang 的 408 文件很感兴趣，想共享这个文件，现在能想到的方法就是，拷贝一份这个文件，放到 xiaoming 目录下，但是这样不太好，首先，在磁盘上存储了 2 份一模一样的文件数据，浪费空间，其次，如果 laotang 修改了 408 文件中的数据，xiaoming 是看不到最新的数据，要解决这种文件共享的问题，有两种方式，分别是硬链接和符号链接，符号链接也叫软链接

硬链接

硬链接是基于文件索引结点来实现的，还是以 xiaoming 想共享 laotang 的 408 文件为例，首先，在文件系统中，对于 laotang 这个目录，会有 3 个目录项，而 xiaoming 目录有 2 个目录项（看下图）
408 这个文件在文件系统中，有对应的 inode，它的 inode 号是 8，在 inode 中，保存着这个文件的属性，其中有一个属性就是这个文件所有者 owner，很明显这个文件的 owner 是 laotang，inode 还保存着这个文件占用的盘块的盘块号，根据它们可以去访问对应的盘块，也就是可以访问 408 文件中的数据
xiaoming 要想也可以看到 408 文件盘块中的数据，可以在 xiaoming 的目录下，创建一个名为 lt408 的文件，然后在 xiaoming 目录中，添加一个目录项（看下图），文件名就是 lt408，不过它的 inode 号直接指向 408 这个文件对应的 inode，也就是 8
这样，xiaoming 可以通过找到 lt408 对应的 inode 号，就可以访问到 408 文件的 inode，然后通过 inode 中的盘块号，就可以去访问存放在盘块中的数据。这样就通过索引节点来实现了文件的共享，lt408 文件就是文件 408 的硬链接，为什么称为硬链接呢？
在上面的 inode 中还维护了一个引用计数 count 属性，目前 count 等于 2，因为现在有 2 个文件链接到这个 inode，当 laotang 删除 408 文件时，删除了相应的目录项（看下图），此时 8 号 inode 少了一个链接，那么需要将引用计数 count 减 1
注意，这个 inode 不会被删除，而且这个 inode 的 ower 也不会变，还是 laotang，这种链接方式更紧密，原文件删除后，硬链接仍然有效，只要有一个硬链接存在，文件数据就不会被删除
假设现在 xiaoming 也删除了 lt408 这个文件，对应的目录项也被删除了，此时 inode 的引用计数 count 自减 1，count 值等于 0，说明没有任何链接指向这个 inode，此时，就可以真的删除这个 inode
有两个地方用到了 "引用计数"，前面我们看到在系统级打开文件表中的每一项有引用计数，这个表示一个文件被多少个进程打开过；而硬链接中的引用计数是保存在文件 inode 中（即 FCB 中），表示这个文件被链接多少次
inode 中的引用计数也可以称为链接计数

符号链接（软链接）

还是以 xiaoming 想共享 laotang 的 408 文件为例，使用符号链接的话，xiaoming 创建一个名为 lt408 的 LINK 类型的文件（看下图），也会对应一个 inode，其 inode 号是 16，它的 owner 是 xiaoming，引用计数是 1，在 xiaoming 目录的目录项中，有对应的 inode 号，指向这个 inode
然后这个 lt408 文件中，存储的就是要共享文件的绝对路径，如果共享文件绝对路径长度比较小的话，那么直接存储在这个 inode 中，如果共享的文件的路径比较长，那么可能需要为这个链接文件分配一个数据块来存储共享文件的路径
当小明去访问 LINK 类型的 lt408 的文件时，从目录项拿到对应的 inode 号，然后拿到对应 inode 中的共享文件的绝对路径，就可以会去访问这个根目录下的 laotang 目录下的 408 文件，这样也可以实现文件的共享，这里的 lt408 文件就是 408 文件的符号链接
这个时候，只有文件主可以删除文件，也就是只有 laotang 可以删除这个 408 文件，laotang 对 408 这个文件有绝对的控制权，当 laotang 把这个文件删除了，xiaoming 继续访问这个 lt408 时，发现访问文件不存在，此时，就可以将这个 LINK 型文件删除
这里的 lt408 其实就是 408 这个文件的快捷方式，比如，我们在 windows 中，创建一个文件 408.txt 的快捷方式
你完全可以通过快捷方式去访问对应的文件，当你删除快捷方式，不会影响原来的文件，当你删除原来的文件时，再次访问快捷方式时，会提示你文件不存在（看下图）

硬链接 vs 软链接

接下来看下硬链接和符号链接的优缺点，先来看硬链接，如下图：
链接前，C 用户目录下有一个文件，在其索引结点中记住这个文件的 owner 是 c，引用计数（count）是 1；接下来在 B 用户目录下创建了一个硬链接文件，指向 C 用户目录的文件，此时文件的所有者 (owner) 不改变，仍然是 c，不过 inode 的引用计数加 1，变为 2
当拥有者 C 删除这个文件时，i 结点的引用计数值减 1，变为 1，这个 inode 还需要保留，不过，现在有个问题是，这个 inode 的所有者还是 C，那么在统计用户 C 或者用户 B 的目录占用磁盘空间的时候，这个 inode 占用的磁盘空间是属于 C 目录的还是属于 B 目录的呢？这个不好说，对吧，有点不伦不类，这就是硬链接的缺点
而符号链接，就可以解决这个问题，因为只有真正的文件所有者才有一个指向 inode 的指针。链接到该文件上的用户只有路径名，没有指向 inode 的指针。当文件所有者删除文件时，该文件被销毁。以后若试图通过符号链接访问该文件将导致失败，因为系统不能找到该文件。删除符号连接根本不影响该文件
不过符号链接的问题是需要额外的开销。必须读取包含路径的文件，然后要一个目录一个目录地扫描路径，直到找到共享文件的 inode。这些操作也许需要很多次额外的磁盘存取。此外，每个符号链接都需要额外的 inode，以及额外的一个磁盘块用于存储路径，虽然如果路径名很短，作为一种优化，系统可以将它存储在 inode 中；而硬链接就不需要额外的开销，在硬链接文件的目录项中直接指向共享文件的 inode，读写性能都是很好的
以下是硬链接和软链接的区别：
硬链接不能跨文件系统，核心原因是：硬链接直接依赖 inode 编号，而不同文件系统的 inode 编号是独立的，没有全局唯一性； 软链接（符号链接）不依赖 inode，它存储的是目标文件的路径字符串，当你访问软链接时，内核会解析这个路径，不管它在哪个文件系统，只要路径存在就能找到目标文件 ，因此，软链接可以跨文件系统  
硬链接不支持目录，核心是为了防止文件系统目录结构出现循环（环），避免破坏文件系统的树形结构，看下图，如果硬链接  /laotang/408/os  指向目录  /laotang
此时，/laotang 下有子目录 408， /laotang/408/os 又指向 /laotang 本身，就形成了目录环，这样的话会发生遍历死循环，find、ls -R、备份工具等递归遍历目录的程序，会陷入无限循环，永远无法遍历完所有目录
