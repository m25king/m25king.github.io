皮特森（Peterson）算法主要是为了解决两个进程（或线程）之间的互斥问题而设计的，它只适用于两个进程的情况

当需要处理两个以上进程的互斥问题时，皮特森算法就不再适用了，就需要我们课上学习的原子操作实现的自旋锁或者阻塞互斥锁了

实际上，像这种皮特森算法才是严格意义上的纯软件实现的互斥锁，没有使用到原子操作，而前面我们学习的自旋锁和阻塞互斥锁都用到了原子操作，因为原子操作是硬件提供的，所以前面我们学习的自旋锁和阻塞互斥锁不能称为纯软件实现

不过，如果不使用原子操作的，而是用纯软件实现多个线程互斥的话，非常的复杂，而且容易出现死锁，所以，在工业级别的编程语言中，基本都是基于原子操作来实现互斥锁，这里大家了解下即可

拓展：在实现进程互斥时，都应该遵循的四条准则

① 空闲让进：当无进程处于临界区时，表明临界资源处于空闲状态，应允许一个请求进入临界区的进程立即进入自己的临界区，以有效地利用临界资源

② 忙则等待：当已有进程进入临界区时，表明临界资源正在被访问，因而其它试图进入临界区的进程必须等待，以保证对临界资源的互斥访问


③ 有限等待：对要求访问临界资源的进程，应保证在有限时间内能进入自己的临界区，以免陷入"死等" 状态，其实就是说，不能出现饥饿现象


④ 让权等待：当进程不能进入自己的临界区时，应立即释放处理机，以免进程陷入"忙等" 状态


上面的皮特森（Peteson）实现互斥的方法，很明显，遵循了空闲让进、忙则等待以及有限等待（不会出现饥饿），但是皮特森（Peteson）实现方法并没有遵循让权等待，因为当一个进程不能进入临界区时，该进程自旋，不会释放处理机，也就是说处于忙等状态


实际上，前面我们学习的自旋锁，都没有遵循让权等待这个准则，只有前面我们学习的阻塞互斥锁遵循了让权等待，因为当一个进程不能进入临界区时，该进程会阻塞，放弃 CPU 执行权

例如：某进程在临界区中运行时，若其时间片耗尽，操作系统仍会触发调度，将 CPU 分配给就绪态中优先级最高的进程

被抢占的进程不会退出临界区，临界区代码执行也不是原子性的，临界区代码可能较长，时间片到后进程会被暂停，但其已通过互斥机制（使用自旋锁或者阻塞互斥锁）锁定共享资源，其他进程无法进入临界区，直到该进程再次获得 CPU 并释放资源

再比如：计算机系统只有一台打印机，现在进程 A 在使用打印机这个临界资源，很明显，为了提升 CPU 利用率，此时，CPU 应该调度执行其他的进程

所以说，进程是否在临界区，不影响处理机调度的触发。C 错误，本题选 C

选项 D：在系统调用完成并返回用户态时能进行处理机调度，系统调用是进程请求操作系统服务（如文件读写、内存分配）的过程，此时进程会从用户态切换到内核态。当系统调用完成并返回用户态时，操作系统会检查是否需要重新调度（例如，若就绪态中有更高优先级进程），因此会触发处理机调度。D 正确

对于 D，你可能还不理解，我来尝试解释下，不过在解释之前，我们先来梳理下发生 CPU 调度的时机点

虽然，我们已经在【CPU 调度的 2 个准备知识点】下方的视频中有讲，但是，现在再来总结下，你可能印象更深刻

在单处理器多进程系统中，处理机调度的核心目标是动态、高效、公平地分配 CPU 资源，因此调度时机的设计会覆盖进程状态变化、CPU 使用权移交、系统事件触发等关键场景。所有的调度时机点，可以分为被动触发和主动触发两大类

一、被动调度时机：进程被迫放弃 CPU时（必须调度）


这类时机的本质是当前运行进程因自身原因无法继续占用 CPU（如阻塞、终止），必须释放 CPU 资源，此时内核必须触发调度，从就绪队列中选择新进程运行，避免 CPU 空闲


1. 进程终止（退出）时


当进程执行完所有任务（如 main 函数返回）或主动调用 exit 系统调用终止时，进程会从运行态变为终止态（最终被内核回收资源）

此时 CPU 失去当前占用者，内核必须立即调度就绪队列中的进程，分配 CPU 使用权，避免 CPU 空闲浪费


2. 进程因 I/O 操作阻塞时


当进程需要等待 I/O 完成（如磁盘读写、网络数据接收、键盘输入）时，会调用 read/write 等 I/O 类系统调用，内核会将其从运行态切换到阻塞态（放入 I/O 等待队列），此时 CPU 被释放，必须触发调度


3. 进程等待某事件（非 I/O 阻塞）时


除了 I/O，进程还可能因等待其他内核事件而阻塞，例如：

  • 调用 waitpid 等待子进程终止
  • 调用 lock 获得阻塞互斥锁（如果没有获的锁，那么就需要阻塞）
  • 调用 sleep 主动挂起一段时间，进程 C 调用sleep(5)（主动挂起 5 秒），内核将其阻塞

这些操作会让进程从运行态进入阻塞态，释放 CPU，触发调度

二、主动调度时机：进程 "仍可运行，但需检查是否切换" 时（按需调度）


这类时机的本质是当前运行进程仍有能力继续执行，但内核为了全局最优（如公平性、实时性），主动检查是否需要切换进程，避免高优先级进程饥饿或低优先级进程长期占用 CPU


1. 时间片耗尽时


在时间片轮转调度算法（最常用的公平调度策略）中，每个进程会被分配一个固定的时间片（如 10ms）。当内核的 时钟中断处理程序检测到当前进程的时间片已用完时，会将其从运行态切换到就绪态，并触发调度，选择下一个就绪进程运行


2. 高优先级进程进入就绪态时


在抢占式优先级调度算法（常用于实时系统）中，若一个更高优先级的进程从阻塞态切换到就绪态（如 I/O 完成、信号触发），内核会立即抢占当前运行的低优先级进程，触发调度，让高优先级进程优先运行，保证实时性


比如：实时系统中，进程 F（高优先级，负责工业设备控制）的传感器 I/O 完成，从阻塞态变为就绪态，内核会立即暂停当前运行的低优先级进程 G，调度 F 运行，避免设备控制延迟


3. 进程主动放弃 CPU（yield）时


部分操作系统提供 yield 系统调用，允许进程主动让出 CPU（从运行态变为就绪态），适用于进程执行完一段非紧急任务后，希望给其他进程机会的场景。当进程调用 yield 时，内核会触发调度，选择就绪队列中的进程运行


接下来，我们来解释【为什么要在系统调用完成并返回用户态时进行处理机调度？】


你有没有想过这样一个问题：在抢占式优先级调度系统中，如果一个很高优先级的进程到达就绪队列时，CPU 调度程序如何调度这个进程执行呢？

CPU 总不能时时刻刻的监视就绪队列吧，如果 CPU 时时刻刻监视就绪队列，完全可以保证马上调度高优先级的进程，但是 CPU 时时刻刻监视就绪队列了，那谁去执行进程，对吧

既然 CPU 不能时时刻刻监视就绪队列，那么系统就应该给到一些让 CPU 去查看就绪队列有没有高优先级进程到达的时机点，比如，上面我们整理的主动调度时机点和被动调度时机点，都是查看就绪队列，然后调度高优先级进程的时机点


但是，如果整个系统都没有发生上面介绍的 6 种调度时机点的话，此时高优先级进程到达就绪队列，如何保证即使调度这个进程呢？


来举一个例子，CPU 正在执行一个低优先级的 "文件备份" 进程（无 I/O 阻塞，写文件时，直接写到页面缓存，时间片还剩 5 秒），此时用户发起一个高优先级的 "实时视频通话" 进程（到达就绪队列）。由于 "文件备份" 进程既不阻塞、也不终止、时间片未到，上述 6 种调度时机都未触发，若没有额外的检查节点，"视频通话" 进程会一直等待，直到 "文件备份" 进程的时间片耗尽（5 秒后），这显然违背了抢占式调度 "高优先级优先" 的核心原则


此时，如果在系统调用完成并返回用户态时进行 CPU 调度，就可以解决上面违背抢占式调度的核心原则的问题


若 "文件备份" 进程在执行中发起了一个 write 系统调用，系统调用完成后，内核在返回用户态前会检查就绪队列，发现 "视频通话" 高优先级进程已到达，此时就会触发调度：暂停 "文件备份" 进程，将 CPU 分配给 "视频通话" 进程，无需等待时间片耗尽，完美实现了抢占


CPU 无法时刻监视就绪队列，只能靠关键事件节点触发调度。现有调度时机（终止、阻塞、时间片耗尽等）覆盖了进程状态异常变化的场景，但无法覆盖进程正常运行、仅高优先级进程新到达的场景


而系统调用返回用户态正是内核设置的 "兜底时机" ： 利用系统调用的高频性和内核态的权限，强制 CPU 在继续执行低优先级用户进程前，最后检查一次就绪队列，确保高优先级进程不会因 "无其他调度时机" 而被长期阻塞，最终保障抢占式调度的有效性和实时性


系统调用的频率通常较高（如普通应用每秒可能发起数十次系统调用），但每次检查就绪队列的开销极低（仅需遍历就绪队列的优先级标识，而非全量扫描）。这种高频低耗的特性，既能保证高优先级进程在秒级甚至毫秒级内被调度，又不会像实时监视那样占用大量 CPU 资源

前面我们说过，在实现进程互斥时，都应该遵循的四条准则

① 空闲让进：当无进程处于临界区时，表明临界资源处于空闲状态，应允许一个请求进入临界区的进程立即进入自己的临界区，以有效地利用临界资源

② 忙则等待：当已有进程进入临界区时，表明临界资源正在被访问，因而其它试图进入临界区的进程必须等待，以保证对临界资源的互斥访问

③ 有限等待：对要求访问临界资源的进程，应保证在有限时间内能进入自己的临界区，以免陷入"死等" 状态，其实就是说，不能出现饥饿现象

④ 让权等待：当进程不能进入自己的临界区时，应立即释放处理机，以免进程陷入"忙等" 状态

接下来来分析每一个描述

I：两个进程不能同时进入临界区，这个符合忙则等待这个准则，就是如果临界区有一个进程的话，那么其他的进程要想进入临界区的话，则需要等待，所以 I 是正确的

II：允许进程访问空闲的临界资源，这个符合空闲让进的准则，所以 II 是正确的

III：进程等待进入临界区的时间是有限的，这个符合有限等待的准则，一个进程不能死等下去，所以 III 是正确的

IV：不能进入临界区的执行态进程立即放弃 CPU，这个虽然符合让权等待这个准则，但是它不是必须要遵守的（比如前面我们学习的自旋锁，完全可以实现互斥，但是没有进入临界区的线程没有放弃 CPU，而是在执行 while 循环自旋呢），所以 IV 描述错误

因此，I、II、III 都是实现临界区互斥机制必须遵循，本题选 C

【22-23】下列关于多道程序系统的叙述中，不正确的是 ( )。

A.支持进程的并发执行

A. 支持进程的并发执行：多道程序系统的核心特征是允许多个程序同时进入内存并交替在 CPU 上运行，实现进程的并发执行。这一特性使得 CPU 在等待某一进程 I/O 操作时，可切换到其他进程运行，提高资源利用率。因此该叙述正确

B. 不必支持虚拟存储管理：虚拟存储管理的主要作用是扩大程序的地址空间（突破物理内存限制），而多道程序系统的核心是支持多进程并发执行，只需内存能同时容纳多个程序即可。早期的多道程序系统（没有虚拟内存技术的系统）也能正常工作，因此多道程序系统不必强制支持虚拟存储管理，该叙述正确


这里不理解的话，请复习：连续分配存储管理方式


C. 需要实现对共享资源的管理：多道程序系统中，多个进程会共享 CPU、内存、I/O 设备等资源。为避免资源竞争导致的冲突（比如数据不一致），操作系统必须实现对共享资源的合理分配与管理（如互斥访问、同步机制）。因此该叙述正确


D. 进程数越多 CPU 利用率越高：进程数增加时，CPU 利用率在一定范围内会提高（因为 CPU 可在更多进程间切换，减少空闲时间）。但当进程数过多时，会导致：
  • 内存资源紧张，频繁的页面置换（若有虚拟内存）或进程切换开销急剧增加
  • CPU 大部分时间用于进程上下文切换，而非执行进程指令，反而会降低 CPU 利用率

因此，CPU 利用率并非随进程数增加而单调升高，该叙述不正确，本题选 D
