空闲分区表

动态分区分配又称为可变分区分配，它是根据应用程序的实际需要，动态地为之分配内存空间，动态分区分配中，内核会维护一张空闲分区表（看下图），一开始的时候，因为整个用户空间都是空闲的，所以这张表只有一个表项，表示这个用户分区可以分配
看下图，应用程序 A 需要 38KB 内存，内核找到空闲分区表，从空闲分区表的 0 号分区中，分配 38KB 给应用程序 A，然后将 0 号空闲分区的起始地址修改为 166，大小修改为 858，也就是减去这个 38KB 已分配的空间
接下来，看下图，应用程序 B 需要 130KB 内存，内核从 0 号分区中，分配 130KB 给应用程序 B，它的起始地址是 166K；应用程序 C 需要 201KB 内存，内核从 0 号分区中，分配 201KB 给应用程序 B，它的起始地址是 296K，现在空闲分区表中的 0 号分区的起始地址变为 497K，大小是 527KB
现在应用程序 B 执行完了，释放占用的连续内存空间，此时多了一个空闲分区，那么在空闲分区表中，会新增一项，这一项的起始地址是 166，大小是 130，然后按照起始地址升序排列，将这一项插入到空闲分区表适当的位置，看下图：
现在应用程序 D 需要 150KB 的内存，那么内核从空闲分区表中，找到一个大于 150KB 的空闲分区，就是上图的 1 号分区，然后将 150KB 的连续内存空间分配给应用程序 D，其起始地址是 497K（看下图），此时 1 号分区的起始地址修改为  647K，大小修改为 377KB；现在应用程序 E 需要 150KB 的内存，那么内核从空闲分区表中，找到一个大于 150KB 的空闲分区，还是 1 号分区（因为现在 1 号分区大小 377KB > 150KB），然后将 150KB 的连续内存空间分配给应用程序 E，然后将 1 号分区的起始地址修改为 797K，大小修改为 227KB，看下图：

空闲分区链

所谓空闲分区链，就是将空闲分区组织成一个双链表，每个结点使用起始地址和大小两个属性，来表示一个空闲分区，看下图双链表中的每个结点表示一个空闲分区，下图用户空闲有 3 个空闲分区，之所以使用双向链表，是因为每个结点，可以通过 prev 指针就可以找到前一个结点，这样可以很快的实现分区的合并操作
上图的空闲分区链，按照内存起始地址升序排列，基于这个空闲分区链也可以实现内存的分配和释放，比如，现在应用程序 C 执行完了，需要释放对应的 201KB 的内存，内核从链表表头查找第一个空闲分区，它的起始地址 + 大小，刚好等于 296K，也就是等于现在要释放的内存区域的起始地址，因此，应用程序 C 释放的内存可以和第一个空闲分区合并，然后，再计算应用程序 C 的起始地址 + 大小 = 497K，也就是等于上图第二个分区的起始地址，所以这个释放的内存区域也可以和后面的空闲分区合并，看下图：
上图直接将 3 个空闲分区合并成一个空闲分区（第一个空闲分区），起始地址是 128K，大小是 168KB + 201KB + 150KB = 519KB，这样，整个用户空间就只有 2 个空闲分区

内存分配流程

分配内存是指系统利用某种分配算法，从空闲分区链表中找到所需大小的分区。设请求的分区大小为 u.size，表中每个空闲分区的大小为 m.size。若 m.size - u.size ≤ size（size 是事先规定的不再切割的剩余分区的大小），则说明多余部分太小，可不再切割，并将整个分区分配给请求者。否则（即多余部分超过 size），从该分区中按请求的大小，划分出一块内存空间并分配出去，余下的部分仍留在空闲分区链表中；然后，将分配区的起始地址返回给调用者。下图所示为内存分配流程

内存回收流程

当进程运行完毕而须释放内存时，系统会根据回收区的起始地址，从空闲分区链表中找到相应的插入点，此时可能会出现以下四种情况之一
① 回收区与插入点的前一个空闲分区 F1 相邻接，如下图（a）所示。此时应将回收区与插入点的前一分区合并，不必为回收分区分配新表项，而只须修改其前一分区 F1 的大小
② 回收区与插入点的后一个空闲分区 F2 相邻接，如上图（b）所示。此时可将两分区合并，形成新的空闲分区，但须将回收区的起始地址作为新空闲区的起始地址，分区大小为两者之和
③ 回收区同时与插入点的前、后两个分区邻接，如上图（c）所示。此时将三个分区合并，使用 F1 的表项和起始地址，取消 F2 的表项，分区大小为三者之和
④ 回收区既不与 F1 邻接，也不与 F2 邻接。这时应为回收区单独建立一个新表项，填写回收区的起始地址和大小，并根据其起始地址将其插入空闲分区链表中的适当位置
