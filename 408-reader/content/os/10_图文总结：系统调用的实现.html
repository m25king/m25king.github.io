我们知道操作系统其实就是由很多的中断/异常服务程序、系统调用服务程序责成的，我们后续的课程中会详细的学习操作系统中的重要的服务程序，对于中断/异常的处理流程我们已经比较清楚了，现在我们再来看看系统调用的处理流程，因为系统调用可以使用软中断来实现，所以在学习系统调用之前，我们先来看看软中断

硬中断和软中断

到现在为止，我们遇到的中断都是 I/O 硬件发出来的，这种外部中断也称为硬中断，还有一类中断是由软件发出来的中断，称为软中断
比如，在 CPU 执行应用程序 A 的时候，执行一条 int 3 指令（这里的 int 是 interrupt 的缩写），这是一条中断指令，执行这条指令，会触发一个中断，因为 int 指令后跟的是 3，所以触发的是 3 号中断，然后根据中断向量表，找到内核中的 3 号中断服务程序的基地址，然后去执行 3 号中断服务程序
软中断和硬中断的处理流程是一样的，当 CPU 执行 int 指令时，触发一个软中断，然后 CPU 响应这个软中断，通过中断隐指令来关中断、保存断点和程序状态字以及跳转执行中断服务程序，在中断服务程序中也包括保存现场、中断服务、恢复现场、开中断以及中断返回

系统调用

内核中的程序接口是 OS 专门为用户程序而设置的（看下图），被提供给了程序员在编程时使用，其也是用户程序取得 OS 服务的唯一途径
程序接口由一组系统调用（systemcall）组成，因此可以说，系统调用提供了用户程序和 OS 内核之间的接口。系统调用不仅可供所有的应用程序使用，还可供 OS 自身使用。在每个系统中，通常有几十条甚至上百条系统调用，每一个系统调用都是一个能完成特定功能的子程序，那么系统调用具体是如何实现的呢？
来看下面一段 C 程序，main 函数和 add 函数都是属于应用程序，它们在用户态执行，在 main 函数中调用的 printf 函数则是属于 stdlib.h 中的库函数，这些库函数一般放在 glibc 这种 C 程序标准库中，glibc 库函数也都是在用户态执行，printf 的作用是将数据送到显示器中显示，这里需要设计操作显示器这个硬件资源，前面我们说过，只有 OS 才可以操作硬件资源，所以肯定需要在内核中执行 I/O 指令 out 来实现将数据送到显示器这个输出设备中，这个 I/O 指令必须是工作在内核态的
所以，工作在用户态的 printf 函数，经过一系列的调用函数后，最终在用户态执行 write 函数，然后必定要陷入到内核态，执行系统调用 write，这个时候需要从用户态切换到内核态，然后系统调用 write 会调用对应的系统调用服务程序 sys_write，在这个系统调用服务程序中肯定会有对应的 I/O 指令，将数据送到显示器中显示
在上面的程序执行过程中，不管是处于用户态还是内核态，就是简单的函数调用函数（即过程调用），比如 main 函数调用 printf 函数、write 函数调用 sys_write 函数，这些普通的函数调用实现是通过 call 调用指令来实现的，这个我们在计组第 4 章详细的学习了，现在的问题是，看上图中，如何实现从用户态陷入内核态呢？就是说如何实现系统调用呢？有 2 种方式实现，一种是通过软中断实现，另一种是通过 syscall 指令实现，我们分别来看

软中断实现系统调用

在 X86 系统中，使用 128 号中断（十六进制是 0x80，所以简称 80 中断）来实现系统调用，当用户程序想要进行系统调用时，在用户态执行一条 int $0x80 指令，这条指令触发一个 80 软中断，既然是中断，那么 CPU 响应和处理 80 软中断的过程就和计组中讲的过程是一样的了，看下图（假设不支持多重中断）：
执行指令 int $0x80 触发软中断，CPU 进行中断响应，先关中断，再保存断点和程序状态，接下来切换到内核态（就是修改标志寄存器中的位模式，这步是比计组中的流程多的一步，也是由 CPU 硬件完成的），然后根据中断向量号 128 去中断向量表中查找中断处理程序入口并跳转；接下来进行中断处理，首先保存现场，再执行对应的系统调用服务程序，然后恢复现场，再开中断，最后中断返回，当系统调用执行完，需要切回到用户态，然后返回到指令 int $0x80 的下一条指令执行，所以说，系统调用结束后，是返回到系统调用指令的下一条指令执行
接下来，我们来详细看下 32 位的 X86 操作系统具体是如何通过软中断实现系统调用的（看下图），首先应用程序调用 printf 函数，在用户态下执行库函数，接下来需要进行系统调用，库函数完成 3 步：① 将参数保存到寄存器中；② 根据系统调用名称得到系统调用号，并暂存在寄存器 eax 中；③ 执行 int $0x80，触发软中断
接下来 CPU 响应 80 中断，首先关中断；然后保存断点和程序状态到 pt_regs 中，这个 pe_regs 其实就是内核栈中的一块栈内存，在 pt_regs 中的程序计数器 ip 就是断点，标志寄存器就是程序状态；接下来就是修改标志寄存器中的位模式，将用户态切换成内核态，最后就是跳转执行 80 中断服务程序
从这里也可以知道为什么将保存程序状态这一步放在 CPU 响应中断阶段了，就是因为在 CPU 响应中断阶段需要修改程序状态（比如这里的标志寄存器的位模式），在修改程序状态之前，需要先将其保存到 pt_regs 栈内存中
在执行 80 中断服务程序时首先是保存现场，会将 CPU 中的通用寄存器（比如 esp、eax、ebx、ecx 等）都保存到 pt_regs 栈内存中；然后 80 中断服务程序根据 pt_regs 中 orig_ax 中保存的系统调用号，去系统调用表（sys_call_table）中找到对应的系统调用函数，比如上图是 printf 函数触发的系统调用，就是 write 系统调用，它的系统调用号是 2，然后就可以直接去执行 write 系统调用服务程序 sys_write ，在执行 sys_write 程序之前，会从 pt_regs 中拿到对应的参数，当系统调用服务程序执行完后，结果会放在 pt_regs 中的 ax 变量中
接下来执行 iret 指令，首先是恢复现场，就是将 pt_regs 栈内存中的数据恢复到 CPU 中对应的寄存器中，比如函数栈栈顶指针恢复到 esp 寄存器中，存放在 ax 中的结果恢复到 eax 寄存器中，还有恢复程序状态（即恢复标志寄存器）；接下来开中断；再接下来就是中断返回，此时标志寄存器中的位模式是用户态（因为之前在 CPU 响应中断阶段保存的程序状态中的位模式是用户态的），现在回到用户态执行库函数，库函数从寄存器 eax 中拿到系统调用的结果，作为返回值给到应用程序执行的函数 printf，以下是整个流程：

syscall 实现系统调用

以上是 32 位 X86 系统采用软中断实现系统调用，在现代的 64 位 X86 系统中，更多是采用 syscall 指令来实现系统调用，64 位 X86 系统实现的系统调用的过程和 32 位的整体上是一样的，只是有 3 个地方不同，看下图：
① 它们的寄存器名称不同，我们知道 32 位 X86 系统的 CPU 寄存器的名字一般都是 e 开头的，而 64 位 X86 系统的 CPU 寄存器的名字一般是 r 开头的
② 在 64 位 X86 系统中，在用户态需要系统调用时，执行的是 syscall 指令，CPU 在执行这条指令时，会自动完成开中断、保存断点和程序状态、切换内核态、以及根据 CPU 中特殊模块寄存器中的地址，直接找到系统调用服务程序并跳转执行，执行 syscall 因为不是中断，也就不需要查询中断向量表，而是直接从寄存器中拿到系统调用服务程序的内存地址，这样可以提高系统调用的性能
③ 64 位 X86 系统中，执行完系统调用服务程序后，是通过执行 sysretq 指令返回到用户态的
