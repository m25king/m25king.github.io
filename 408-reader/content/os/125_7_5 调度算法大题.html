【16-46】（6 分）某进程调度程序采用基于优先数 (priority) 的调度策略，即选择优先数最小的进程运行，进程创建时由用户指定一个 nice 作为静态优先数。为了动态调整优先数，引入运行时间 cpuTime 和等待时间 waitTime，初值均为 0。进程处于执行态时，cpuTime 定时加 1，且 waitTime 置 0；进程处于就绪态时，cpuTime 置 0，waitTime 定时加 1。请回答下列问题。

(1) 若调度程序只将 nice 的值作为进程的优先数，即 priority = nice，则可能会出现饥饿现象，为什么?（2 分）

(2) 使用 nice、cpuTime 和 waitTime 设计一种动态优先数计算方法，以避免产生饥饿现象，并说明 waitTime 的作用。（4 分）

（1）因为调度程序使用静态优先数 nice，当系统不断的有优先数高的进程到达时，那么优先数 nice 低的进程可能永远得不到调度执行，所以，也就出现了饥饿现象了

（2）注意，一定要看清题目，题目规定采用基于优先数的调度策略，选择优先数最小的进程运行，也就是说，不管采用静态优先数，还是动态优先数，都是优先数越小的进程，越需要被先调度执行

要避免产生饥饿的话，就需要当一个进程等待的时间越久，它的动态优先数应该越小，也就说进程的动态优先数应该和等待时间 waitTime 成反比

而且，题目还给了一个静态优先数 nice，很明显，进程 nice 值越小，那么越需要被调度，那么对应的动态优先数应该越小，所以进程的动态优先数和 nice 成正比

按照【高响应比优先调度算法】计算动态优先级的思路，我们在这里，可以设计进程的动态优先数 = nice / waitTime 

这样看起来 waitTime 越长，nice 值越小，进程的动态优先数越小，进程就会越需要先调度执行

但是题目说了 waitTime 可以是 0（初始值为 0，进程处于执行态时也是 0），如果 waitTime = 0 的话，上面的动态优先数的计算公式就会出现异常，所以这样做除法时不对的

在初始时，waitTime 等于 0，那么可以直接以 nice 作为动态优先数，也就是说，所有的进程刚启动的时候，它的优先数就看 nice 就可以，这个很合理

当进程处于就绪态时，这个时候要使的动态优先数和 waitTime 成反比，此时 waitTime 是不断增加的（定时加 1），实现反比除了除法，还有减法

所以，设计进程的动态优先数 = nice - waitTime，这里 nice 值越小，waitTime 越大，那么动态优先数就会越小，从而可以增加进程被选择的机会

当进程处于执行态时，因为 waitTime = 0，如果还是以进程的动态优先数 = nice - waitTime，那么此时进程的动态优先数就等于 nice 值了，如果进程的 nice 值非常非常小的话，那么这种进程也会一直被调度执行，使得 nice 值比较大的进程得不到执行

为了防止这种情况，我们还需要考虑进程的执行时间 cpuTime，当 nice 值很小的进程，如果 cpuTime 越长的话，那么应该增加这个进程的动态优先数（也就是降低这个进程的优先权），使得其他优先数小的进程来抢占这个进程

所以当进程处于执行态时，设计进程的动态优先数 = nice + cpuTime，这样的话，当 cpuTime 增加，进程的动态优先数也增加，即使这个进程的 nice 值很小，当它执行了很长时间后，它的动态优先数也会很大，从而被其他优先数比较小的进程来抢占

综上，进程的动态优先数 priority = nice + cpuTime - waitTime

cpuTime 的作用：进程运行时间越长（cpuTime 越大），priority 值越大（优先权降低），防止进程长期占用 CPU

waitTime 的作用：进程等待时间越长（waitTime 越大），priority 值越小（优先权升高），确保长期等待的进程（即使初始 nice 值较大）能逐步获得更高优先级，最终被调度执行，避免饥饿

waitTime 是避免饥饿的关键：它为长期处于就绪态的低优先级进程提供了 "优先级补偿" 机制。即使某个进程初始 nice 值较大（优先权低），但随着等待时间累积，waitTime 增大将显著降低其 priority 值，使其优先权逐渐超过那些长期运行的高优先权进程，最终获得 CPU 资源，从而彻底避免饥饿现象


我觉得如果能给到  priority = nice + cpuTime - waitTime 这个公式，应该就可以拿满分了，不过，标准答案好像还考虑了比例因子，请看下面


拓展：为 cpuTime 和 waitTime 引入比例因子（权重）确实能让动态优先级的调整更灵活、更符合实际需求

在实际系统中，cpuTime（惩罚长期运行的进程）和 waitTime（补偿长期等待的进程）的重要性可能不同：
  • 若希望更严格地限制进程连续运行时间（比如实时系统），可以给 cpuTime 更大的权重
  • 若希望更快地解救饥饿进程（比如交互式系统），可以给 waitTime 更大的权重。

因此，加入比例因子后的计算公式可以是：进程的动态优先数 priority = nice + α * cpuTime - β * waitTime


其中，α 和 β 是正的比例因子（可根据系统需求调整），有了比例因子后，可以：

① 灵活调整调度倾向：
  • 增大 α：促使 CPU 资源更快地从长运行进程转移到其他进程
  • 增大 β：让饥饿进程更快提升优先级，减少等待时间

② 适配不同场景，比如：
  • 在服务器系统（比如 Web 服务器）中可能设置 α < β，优先保证等待的任务能及时处理
  • 在计算密集型系统中可能设置 α > β，允许进程相对长时间运行以减少切换开销

这种设计保留了基本逻辑的同时，通过参数调优让调度策略更具适应性，是操作系统中动态优先级调度的常见优化方式
